# Lab 19: Securing Kubernetes with RBAC and Service Accounts

## Overview
This lab implements Role-Based Access Control (RBAC) to secure Kubernetes resources by creating a ServiceAccount, Role, and RoleBinding that restrict permissions to creating and updating deployments within the `ivolve` namespace.

## Components

### Service Account: jenkinsSA
- **Name**: `jenkinsSA`
- **Namespace**: `ivolve`
- **Purpose**: Identity for Jenkins CI/CD to interact with the cluster
- **Token**: Automatically generated by Kubernetes (stored as a Secret)

### Role: ivolveDeployRole
- **Name**: `ivolveDeployRole`
- **Namespace**: `ivolve`
- **API Groups**: `apps`
- **Resources**: `deployments`
- **Verbs**: `create`, `update`
- **Purpose**: Grants permission to create and update Deployment resources only

### RoleBinding: ivolveDeployRoleBinding
- **Name**: `ivolveDeployRoleBinding`
- **Namespace**: `ivolve`
- **Subject**: ServiceAccount `jenkinsSA` in namespace `ivolve`
- **Role**: `ivolveDeployRole`
- **Purpose**: Binds the role to the service account within the namespace

## Deployment

```bash
# Apply all RBAC resources
kubectl apply -f rbac.yaml

# Or apply individually
kubectl apply -f rbac.yaml
```

## Validation

### 1. Verify ServiceAccount creation
```bash
kubectl get serviceaccount jenkinsSA -n ivolve
kubectl describe serviceaccount jenkinsSA -n ivolve
```

Expected: ServiceAccount exists with auto-generated token secret

### 2. Verify the ServiceAccount token
```bash
# Get the token secret name
TOKEN_SECRET=$(kubectl get serviceaccount jenkinsSA -n ivolve -o jsonpath='{.secrets[0].name}')

# Get the token value
kubectl get secret $TOKEN_SECRET -n ivolve -o jsonpath='{.data.token}' | base64 --decode
```

### 3. Verify Role permissions
```bash
kubectl get role ivolveDeployRole -n ivolve -o yaml
kubectl describe role ivolveDeployRole -n ivolve
```

Expected output:
```
Rules:
  Type     Resources   Non-Resource URLs   Resource Names   Verbs
  ----     -----------   -----------------   --------------   -----
  apps     deployments                         []           [create update]
```

### 4. Verify RoleBinding
```bash
kubectl get rolebinding ivolveDeployRoleBinding -n ivolve -o yaml
kubectl describe rolebinding ivolveDeployRoleBinding -n ivolve
```

Expected: Subjects includes `jenkinsSA` ServiceAccount, RoleRef points to `ivolveDeployRole`

### 5. Test permitted action (create deployment)
```bash
# As jenkinsSA - should succeed
kubectl auth can-i create deployments --as=system:serviceaccount:ivolve:jenkinsSA -n ivolve
kubectl auth can-i update deployments --as=system:serviceaccount:ivolve:jenkinsSA -n ivolve
```

Expected: `yes`

### 6. Test restricted actions (should be denied)
```bash
# Should be denied - no delete permission
kubectl auth can-i delete deployments --as=system:serviceaccount:ivolve:jenkinsSA -n ivolve

# Should be denied - no access to other namespaces
kubectl auth can-i create deployments --as=system:serviceaccount:ivolve:jenkinsSA -n default

# Should be denied - no access to other resource types
kubectl auth can-i create pods --as=system:serviceaccount:ivolve:jenkinsSA -n ivolve
kubectl auth can-i create services --as=system:serviceaccount:ivolve:jenkinsSA -n ivolve
```

Expected: `no` for all restricted actions

### 7. Verify namespace isolation
```bash
# Role is namespace-scoped, permissions do NOT apply outside ivolve namespace
kubectl auth can-i create deployments --as=system:serviceaccount:ivolve:jenkinsSA -n kube-system
```

Expected: `no`

## Security Principles Demonstrated

1. **Least Privilege**: ServiceAccount only gets the exact permissions needed (create/update deployments)
2. **Namespace Scoping**: Role and RoleBinding are limited to the `ivolve` namespace
3. **Resource Scoping**: Only `deployments` resource is accessible, not pods, services, etc.
4. **Verb Scoping**: Only `create` and `update` verbs allowed, not `delete`, `get`, `list`, etc.
5. **Identity Isolation**: Jenkins uses its own ServiceAccount rather than default or admin credentials

## Notes
- ServiceAccount tokens are automatically mounted in pods that reference the ServiceAccount
- For Jenkins integration, configure Jenkins with the ServiceAccount token for Kubernetes deployments
- The Role is namespace-scoped; it cannot grant permissions across namespaces
- To add more permissions, modify the Role rules or create additional Roles/RoleBindings
